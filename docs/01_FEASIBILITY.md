# 01 可行性评审：Q1 到 Q8

评审日期：2026-11-10。评审对象：项目背景 v2（边学边造的私人贝斯学习工具）。

## 怎么读这份文件

每个结论前面都标了它是哪一类说法：

- **【事实】** 有公开来源或可以直接计算得出。来源列在文末。
- **【推测】** 根据原理和经验做的估计，没有在本项目的设备上测过。每一条推测都在 `02_RISKS_AND_SPIKES.md` 里对应一个验证实验。
- **【判断】** 评审员的建议或取舍，产品负责人可以推翻。

凡是提到具体产品型号，都只是举例，并且**需核实是否仍在售、规格是否有变**。

## 总结论

1. **【判断】这个项目可以做，但前提是换一个起点：先练琴、先用现成工具、先攒数据，应用代码最晚出现。** 最大的风险不在技术，在于“造工具替代了练琴”和“零基础自己摸索养成坏习惯”。
2. **【判断】技术上最难的一段（41 Hz 低音的实时判定）在接线路线下是可解的**，因为引导式练习把问题从“听写”变成了“验证”，并且节奏评分不需要等音高确认。但“验证”带来一个必须正面处理的副作用：系统容易把弹错的判成对的。
3. **【判断】有三处建议换做法**，都写成了提议中的 ADR：
   - 监听默认用“接口直接监听 + 插在接口上的有线耳机”，伴奏也从接口出。AirPods 听伴奏在接线路线下很别扭，第一版不支持（ADR-006，负责人已确认）。
   - 没有 Mac 的情况下，算法必须先在 Windows 上用录音离线做完，iOS 只做薄壳（ADR-005）。到了阶段 2 仍然建议买一台二手 Mac mini（负责人已表示以后会买）。
   - 课程不自己设计，直接采用一套成熟课程作主干，再请真人老师在三个节点把关（`04_CURRICULUM_DRAFT.md`）。

## Q1. 接线路线的具体方案

### 1.1 接线方式有哪几类

| 类别 | 是什么 | 优点 | 问题 | 结论 |
|---|---|---|---|---|
| A. 入门级桌面音频接口（2 进 2 出） | 一个小盒子，有乐器输入、增益旋钮、耳机口、直接监听 | 有实体增益旋钮和削波灯；直接监听成熟；iPhone 和 Windows 都能用；双输入可以多录一路节拍基准 | 体积稍大；部分型号功耗超过 iPhone 的 4.5 W | **推荐** |
| B. 移动端乐器专用接口 | 为手机设计的小型吉他/贝斯接口 | 小、省电、为 iPhone 设计；多数是 1 MΩ 乐器输入 | 通常只有一路输入；有的型号没有真正的直接监听或增益范围窄 | 可接受的备选 |
| C. 带 USB 音频的练习耳放或音箱 | 耳机放大器或小音箱，顺带能当 USB 声卡 | 一个设备解决“听”和“录” | USB 送出的往往是加了音箱模拟和效果的声音，不是干声；【事实】有用户报告某款耳放无法边听 USB 伴奏边录干声；另有厂商支持页面说明某款贝斯音箱的 USB 口在 iOS 上不能收发音频 | 不作为主设备 |
| D. USB 线材式接口 | 一根线，一头大三芯一头 USB | 最便宜、最简单 | 没有增益旋钮、没有监听、输入规格多半不公开；游戏厂商的专用线是 USB-A 口，官方资料没有说支持手机 | 不推荐 |
| E. 耳机孔模拟接口 | 走 3.5 mm 四段插头 | 无 | USB-C 的 iPhone 没有耳机孔 | 排除 |

### 1.2 选型标准

| 项目 | 标准 | 为什么 |
|---|---|---|
| 输入阻抗 | 乐器输入（Hi-Z）至少 500 kΩ，最好 1 MΩ 左右 | 【事实】被动贝斯拾音器输出阻抗高，接到低阻抗输入上会损失电平和高频。高频决定起音是否清晰，起音检测靠它。 |
| 最大输入电平和增益范围 | 增益拧到最小时，用力拨弦不削波；有实体旋钮和削波指示灯。主动电路的贝斯输出更大，需要更高的余量或衰减开关 | 削波会制造假谐波，直接破坏音高检测。实体旋钮让零基础用户能照着“拧到灯刚好不红”来做。 |
| 低频响应 | 规格表写明 20 Hz 起平直 | 确保 41 Hz 基频没有被输入端的高通滤掉。接入检查里也会实测（见 1.4）。 |
| 采样率和位深 | 48 kHz，24 bit 即可 | 【事实】48 kHz 下 41 Hz 一个周期有 1165 个采样，时间分辨率足够。更高采样率只增加计算量。 |
| 硬件直接监听 | 必须有，并且有耳机口。能调琴声和电脑回放的比例最好，至少要有开关 | 琴声不经过 App，没有软件延迟（见 Q3）。 |
| 免驱动 | USB Audio Class 免驱，厂商明确写了支持 iPhone 或 iPad | iOS 不能装驱动。只写“支持 Mac/PC”的要先查清楚。 |
| 供电 | 总线供电并且功耗不超过 4.5 W，或者自带第二个供电口 | 【事实】iPhone 15 及以后给配件最多供 4.5 W。 |
| Windows 支持 | 有 ASIO 驱动 | 开发机是 Windows，录测试集和回放注入都在这台机器上做。 |
| 输入路数 | 两路更好 | 第二路可以把节拍器信号回录进同一个文件，得到采样级对齐的时间基准（见 `05_LEARNING_LOOP.md`）。 |
| 预算 | 【推测】大致 60 到 200 美元一档就够，不需要更贵的 | 价格随地区和时间变化很大，以购买时为准。 |

### 1.3 推荐

**【判断】推荐 A 类：带乐器输入、硬件直接监听、免驱动的入门级桌面 USB-C 音频接口，最好两路输入。**

理由有三条。它同时服务三个场景：iPhone 上练琴、Windows 上录测试集、以后做竞品回放注入。它有实体旋钮和指示灯，零基础用户能照着做。它是音乐行业的通用设备，以后就算不做这个 App 也不浪费。

如果更看重便携，B 类也可以，但必须确认有直接监听。

型号举例（全部**需核实是否仍在售、是否标明支持 iPhone、功耗是否在 4.5 W 以内**）：

- A 类：Focusrite Scarlett Solo 或 2i2、Audient EVO 4、MOTU M2、Steinberg IXO 系列、Zoom AMS-22 或 AMS-24、Roland Rubix22。
- B 类：IK Multimedia iRig HD X（【事实】零售规格标 1 MΩ 输入阻抗、最大输入 +9 dBu，说明书写明有直接监听）、IK Multimedia iRig USB。

买之前只需要做一件事：查该型号的官方页面有没有写 iPhone 或 iPad 支持，查不到就换一个。买到之后第一件事是跑实验 S1（`02_RISKS_AND_SPIKES.md`）。

还需要一副**有线耳机**插在接口上。任何普通有线耳机都行。负责人已有。

**关于负责人的琴：** 是四弦、被动和主动电路可切换的型号（装电池、有音色调节旋钮的就是主动电路）。这对方案有两点影响：

- 主动模式输出更大，被动模式输出阻抗更高。两种模式下接口的合适增益位置不一样。**【判断】练习、录测试集、做竞品实测时固定用一种模式，建议用被动模式**：不依赖电池电量，音色旋钮不参与，录音条件最容易保持一致。用哪种模式要记进每次录音的元数据。
- 切换了模式或者换了电池之后，重新做一次接入体检。主动模式电池快没电时声音会失真，表现很像接口削波。

### 1.4 App 怎样检查接入是否正常

App 启动练习前做一次“接入体检”，分两层。

**第一层：读系统状态，不需要用户做任何事。**

| 检查 | 怎么查 | 不正常时告诉用户什么 |
|---|---|---|
| 输入是不是接口 | 读当前音频路由的输入端口类型，应为 USB 音频 | “现在用的是手机麦克风，请检查 USB 线” |
| 实际采样率 | 激活音频会话后读实际值，不要相信请求值 | 不是 48 kHz 时内部重采样并记录 |
| 实际缓冲大小和系统报告的输入输出延迟 | 同上，读实际值 | 只记录，供评分时钟使用 |
| 通道 | 看哪一路有信号 | “琴插在第 2 路输入上，已自动切换” |

**第二层：让用户弹几下，App 听。**

| 检查 | 用户做什么 | 判定方法（阈值是初始提议，由实验 S2 修正） |
|---|---|---|
| 噪声底 | 手按住所有弦 3 秒 | 有效值应低于约 −60 dBFS。同时看 50 Hz 或 60 Hz 及其倍频有没有突出的峰，有就提示“有电源哼声” |
| 电平 | 用平时最大的力气拨最粗的空弦 4 次 | 峰值落在 −12 到 −3 dBFS 之间算合适。太低提示“把接口增益顺时针拧一点”，太高提示逆时针 |
| 削波 | 同上 | 连续多个采样贴着满刻度就算削波 |
| 低频是否完整 | 同上 | 41 Hz 基频相对二次谐波的能量不应低得离谱，否则提示可能开了高通或设备不合适 |
| 调弦 | 逐根弹空弦 | 每根弦偏差在几个音分以内 |

体检结果存成“这一次练习的输入档案”，和评分结果、录音一起保存。以后复盘某次误判时，先看当时输入是否健康。

### 1.5 怎样引导零基础用户

【判断】引导做成五步，每步一张图加一句话，每步都有“App 听到了”的确认：

1. 把琴上的音量旋钮和 Tone 旋钮都拧到最大。（主动电路的琴顺带检查电池。）
2. 线从琴插到接口上标着 INST 或有吉他图标的输入口，按下 INST 或 Hi-Z 开关。
3. 接口用 USB-C 线接手机，耳机插到接口的耳机口，打开接口上的直接监听。
4. 按 1.4 第二层做三个动作：按住弦、用力拨、逐弦调音。
5. App 显示“全部正常”，并提示记住增益旋钮现在的位置（建议拍张照）。

练习过程中持续监测电平和削波。如果一段时间内“没听清”的比例突然升高，App 先建议重新体检，不给这一段打分。

### 1.6 给麦克风路线预留什么

1. **输入源抽象。** 上层只认“带时间戳的音频流加一份输入档案”，不关心来自接口还是麦克风。
2. **输入档案里带上路线类型和质量参数**（噪声底、预期串音、频响修正）。检测器的阈值按档案取值，不写死。
3. **伴奏参考信号可达。** 麦克风会录到伴奏。分析模块必须能拿到“此刻正在播放的伴奏”，以后才能做串音抑制。现在不实现，只保证数据通路在。
4. **测试集按路线分开。** 接线录音和麦克风录音分目录、分指标，不混在一起算准确率。
5. **评分结果里记录路线。** 以后可以对麦克风路线用更宽的“没听清”区间。

## Q2. 音高和节奏检测

### 2.1 算法候选比较

前提：输入是接口送来的单声道干声，单音为主，谱面已知。

| 候选 | 原理 | 对本项目的好处 | 问题 | 许可 |
|---|---|---|---|---|
| YIN | 时域差分函数找周期 | 成熟、简单、容易自己实现和调试 | 攻击瞬间和余音重叠时会出错；需要手动把最低频率设到 E1 以下 | 算法公开，自己实现无许可问题 |
| MPM（NSDF） | 归一化平方差函数加峰值挑选 | 自带一个“清晰度”数值，天然适合做“没听清”；窗口可以比 YIN 稍短 | 清晰度不等于正确概率，需要用数据标定 | 同上 |
| Cycfi Q 的 BACF | 把信号变成比特流再做自相关 | 【事实】专为拨弦乐器实时检测设计，C++，带信号调理模块；计算量极小 | 作者的性能说法没有独立的贝斯数据验证；内部较难自己改 | MIT |
| pYIN | YIN 多候选加隐马尔可夫平滑 | 离线分析很稳 | 需要前瞻，不适合直接做即时反馈 | 算法公开；librosa 实现是 ISC |
| 神经网络（CREPE 一类） | 从波形直接估音高 | 离线精度高 | 输入窗口 64 ms 起、要移植到手机、难以解释为什么判错；【事实】原模型音域下界约 32.7 Hz，不覆盖五弦低 B | CREPE 仓库 MIT |

### 2.2 第一版推荐

**【判断】实时路径用“能量与谱通量的起音检测”加“MPM 类周期检测做带谱面先验的验证”。Cycfi Q 的 BACF 作为对照候选，用同一批录音比较后再定。神经网络和 pYIN 只在离线使用，帮忙给录音打参考标签。**

理由：

1. 干净的单音信号上，时域周期法已经够用，模型复杂度换不来更多东西。
2. 需要一个能解释的置信度来划“没听清”的线，MPM 的清晰度正好提供起点。
3. 整个项目靠 AI 写代码、负责人不审代码。算法越简单，越能靠“输入录音、输出事件”的测试来保证正确。神经网络出错时没有人能诊断。
4. 最终选哪一个由实验 S2 的数据决定，现在的推荐只是起跑顺序。

### 2.3 “听写变验证”这个假设成立吗

**【判断】成立，但收益主要不在“降低物理延迟”，而在“减少歧义”和“把延迟问题拆开”。**

能带来的好处：

- **搜索空间变小。** 不用在 30 到 400 Hz 里找音高，只需要回答“这是不是 E1，如果不是，是它附近的哪个音”。八度歧义（基频和二次谐波谁是主峰）可以直接用谱面消解，这是低音最常见的误判来源。
- **窗口可以按预期音来定。** 预期是 G2（98 Hz）时只需要大约 20 到 30 ms 的信号，不必按最低音留窗口。
- **延迟问题被拆开。** 节奏评分用的是起音时间戳，起音几毫秒内就能定位。音高确认可以晚 50 到 100 ms 到达，再补到这个音符上。见 2.6。

不能带来的：

- **【推测】最低几个音的确认时间不会有数量级的下降。** 区分 E1（周期 24.27 ms）和 F1（周期 22.91 ms），周期只差 1.36 ms，也就是 48 kHz 下 65 个采样。干净信号上大约需要 1.5 到 2 个周期才能可靠区分，再加上要跳过拨弦最初十来毫秒的不稳定段。所以 E1 的确认时间估计在 50 到 80 ms，这是物理下限附近，先验帮不上更多。由实验 S2 实测。

### 2.4 怎样防止“弹错了却判成对”

这是验证模式的头号风险。五道防线，全部写进提议中的 ADR-003：

1. **先验只用来消解八度歧义，不用来偏袒相邻的音。** 预期音和它上下一两个半音、相邻弦的同品位音、高低八度一起作为候选，用同一把尺子打分。
2. **判对要过两关。** 预期音的得分要比最强的竞争候选高出一个余量，并且绝对清晰度超过阈值。差一关就是“没听清”，不是“对”。
3. **并行跑一个不看谱面的检测器。** 它有把握地报出另一个音时，直接判错并说出是哪个音。两个检测器都没把握时，判“没听清”。
4. **错位谱面测试。** 把任意一段弹对了的录音配上移了半音的谱面去评，结果必须全部判错。这个测试不需要额外录音，能自动产生大量反例，放进 CI。
5. **误收率是一等指标。** 测试集必须包含故意弹错的录音（错半音、错弦、错八度）和完全不弹只放伴奏的录音。“弹错判成对”的比例单独报告，门槛比“弹对判成错”更严。

### 2.5 起音和音高分开；连弹和余音

起音检测和音高检测是两个独立模块，各自输出带时间戳的事件，由对齐模块合并。

| 情况 | 现象 | 处理 |
|---|---|---|
| 同一个音连续弹 | 音高轨迹不变，看不出弹了几次 | 只靠起音模块。手指触弦会让振幅先掉一下再冲起来，并带一个高频瞬态。用高频段能量突增加包络回升来检测，设最小间隔防止一次拨弦报两次 |
| 换弦后上一根弦还在响 | 信号变成两个音叠加，单音假设不成立 | 起音之后拿“起音前一帧”当背景，看预期音的谐波位置上有没有新增能量。新音确认后如果旧音的谐波仍然明显，记一个“上一个音没止住”的标记 |
| 幽灵音、闷音 | 有起音，没有稳定音高 | 输出“有起音、无音高”事件。谱面要求闷音时算对，要求实音时算“没听清”或错，取决于时长和清晰度 |
| 指弹起音偏软 | 起音瞬态不如拨片明显 | 【推测】阈值需要按本人的弹法标定，用自己的录音在实验 S4 里调 |

【判断】“上一个音没止住”很可能是这个 App 相对竞品最有教学价值的反馈，因为闷音从第一课就要练。但它是否测得准还没有证据，第一版不承诺，放在实验 S4 里先看数据。

### 2.6 “没听清”状态，以及它和“弹错”的界线

每个预期音符的判定结果是下面五种之一：

| 结果 | 含义 | 需要的证据 |
|---|---|---|
| 命中 | 弹了，音对。同时附带早晚偏差 | 判定窗口内有起音；预期音过两关 |
| 弹错 | 弹了，但是另一个音 | 有起音；**有把握地识别出另一个具体的音**，能说出“你弹的是 F” |
| 漏弹 | 没弹 | 窗口内没有起音，**并且输入档案健康、电平监测正常** |
| 多弹 | 谱面没有的地方出现了起音 | 起音清晰，不在任何预期音符的窗口内 |
| 没听清 | 系统无法判断 | 见下 |

**界线只有一条：判错必须有正面证据。** 拿不出“你弹的是哪个音”或者“输入正常但确实没有起音”，就只能是“没听清”。

以下任一情况判“没听清”：

- 这个音持续期间输入不健康（削波、电平过低、噪声底过高）。
- 有起音，但到分析窗口结束时清晰度仍不够。常见原因是音太短，不足该音高大约三个周期。
- 预期音和竞争候选的得分差在余量以内。
- 看谱面的检测器和不看谱面的检测器结论不一致，且都没把握。
- 余音重叠导致无法确认新音。

对用户：“没听清”不扣分，用中性颜色显示，一次练习结束后告诉用户有几个音没听清以及最可能的原因。

对系统：“没听清”的比例单独统计，并且设上限。系统不能靠多报“没听清”来掩盖识别能力不足。干净测试集上的初始门槛提议为不超过 5%（见 `03_ROADMAP.md` 关卡 G1）。

### 2.7 端到端延迟预算

条件：接线路线、48 kHz、iPhone 接音频接口。**表里除周期计算外都是【推测】，要用实验 S5 实测替换。**

| 段 | 内容 | 估计时间 | 说明 |
|---|---|---|---|
| 1 | 琴弦振动到接口完成模数转换 | 约 1 ms | 转换器固有延迟 |
| 2 | USB 传输加 iOS 输入缓冲，到 App 拿到数据 | 5 到 12 ms | 缓冲 128 到 256 采样是 2.7 到 5.3 ms，再加系统安全余量。【事实】公开测试里几款接口在 iOS 上 64 采样缓冲的往返延迟是 9 到 15 ms |
| 3 | 起音检测确认 | 5 到 15 ms | 需要看到能量冲起来并过峰 |
| 4 | 音高确认 | E1：50 到 80 ms；A1：35 到 55 ms；D2：27 到 40 ms；G2 及以上：20 到 30 ms | 跳过约 10 ms 攻击段，再取 1.5 到 3 个周期 |
| 5 | 结果送到界面线程 | 1 到 5 ms | |
| 6 | 等下一帧并显示 | 10 到 35 ms | 取决于屏幕是 120 Hz 还是 60 Hz |

合计：

| 反馈 | 从拨弦到屏幕变化 |
|---|---|
| “听到你弹了”（起音提示，带早晚） | 约 25 到 65 ms |
| “音高对不对”，中高音区 | 约 45 到 95 ms |
| “音高对不对”，最低的 E1 | 约 75 到 145 ms |

**两个独立的指标，分别验收：**

| 指标 | 含义 | 目标 | 怎么测 |
|---|---|---|---|
| 评分时间戳准确度 | 系统记录的起音时刻，和真实拨弦时刻差多少 | 系统偏差校准后接近 0，随机误差在正负 5 ms 以内 | 回环测试：接口输出接回输入，播放已知时刻的脉冲（实验 S5）；离线用标注录音核对 |
| 反馈显示及时度 | 从拨弦到屏幕变化要多久 | 起音提示不超过 70 ms；音高结果不超过 150 ms | 用手机慢动作录像同时拍手和屏幕 |

【判断】时间戳准确度是硬指标。初学者的节奏偏差通常是几十毫秒，系统自己的误差必须小一个量级，评分才有意义。显示及时度是软指标：反馈是给人看了之后调整下一个音用的，100 ms 左右到达完全够用。所以界面上做两段式反馈：先亮起音提示和早晚，稍后再上音高颜色。

## Q3. 监听和伴奏

### 3.1 用户怎么听到自己的琴声

**【判断】默认方案：有线耳机插在接口上，打开接口的直接监听。琴声在接口内部直接送到耳机，不经过手机。**

关键的一点是：接口接上 iPhone 之后，它同时也是 iPhone 的输出设备。App 播放的伴奏和节拍器会从同一个耳机口出来。所以一副有线耳机就能同时听到琴声（零软件延迟）和伴奏。

由此定下两条规矩：

- App 第一版**不做软件监听**，不把输入信号送回输出。这样不会出现“直接监听一份、软件监听又一份”的双重声音。
- 琴声和伴奏的音量比例用接口上的旋钮调，App 只管伴奏音量。

### 3.2 AirPods 只听伴奏

**【判断】这条路在接线路线下很别扭，建议第一版不支持。** 原因：

1. **戴着 AirPods 就听不到接口耳机口里的琴声。** 要听琴声只能再开一台音箱，然后用 AirPods 的通透模式。设备更多，声音更乱。
2. **【推测】iOS 上“USB 接口做输入、蓝牙耳机做输出”这种组合能不能稳定选中，没有查到明确保证。** 需要实验 S7。
3. **蓝牙延迟大并且不固定。** 【事实】公开测试里 AirPods Pro 第二代从触发到出声总共约 126 ms，比内置扬声器多约 43 ms，这是 2022 年的数据，不代表现在的机型。每次连接的延迟还可能不同。
4. **输入和输出不在同一个时钟上。** 接口和 AirPods 各走各的时钟，对齐只能靠系统时间戳换算。

如果以后一定要支持，补偿办法是：伴奏是预先知道的，所以可以把“谱面时间零点”定义为“伴奏第一拍到达耳朵的时刻”，也就是计划播放时刻加上输出延迟。这个延迟需要校准流程：

- **客观校准（优先）：** 拔掉接口，让 AirPods 播放一串咔哒声，用手机麦克风贴近耳机录下来，算出延迟。
- **演奏式校准（不推荐作为唯一手段）：** 让用户跟着节拍器弹十几下取中位数。它会把用户自己抢拍或拖拍的习惯一起“校准掉”，而这正是 App 要教的东西。
- 每次换耳机、重新连接之后都要重新确认；这种模式下的节奏评分要标成“参考”，容差放宽。

### 3.3 伴奏、谱面、评分时钟怎样对齐

**原则：全系统只有一个时钟，就是音频硬件的采样时钟。屏幕和评分都跟它走，不用定时器，不用系统墙上时间。**

1. **伴奏**用“在指定采样时刻开始播放”的方式调度，不用“现在就播”。
2. **音乐时间零点 T0** = 伴奏第一拍的计划播放时刻 + 输出延迟 + 该路线的校准值。它表示第一拍到达耳朵的时刻。
3. **谱面**通过速度表把拍子换算成秒。第 i 个音符的预期时刻 = T0 + t_i。
4. **输入**的每个缓冲区都带着采样时间。起音时刻 = 缓冲区起始时间 + 起音在缓冲区内的位置 − 输入延迟 − 校准值。
5. **屏幕**上的播放头位置，每一帧都由“当前时间 − T0”现算出来。屏幕是从属的，卡一帧也不会累积误差。
6. **校准值**由回环测试得到（接口输出用一根线接回输入，播放脉冲、录回来、量差值），按“设备加路线”保存。

接口同时做输入和输出还有一个好处：输入输出共用一个硬件时钟，不存在两个设备之间的漂移。这是推荐全有线方案的又一个理由。

## Q4. 没有 Mac 的开发可行性

### 4.1 “CI 构建 → TestFlight → 真机”循环能不能撑住

**【判断】撑得住发布，撑不住实时音频的调试。**

- 【推测】一轮循环（推送、macOS runner 构建、上传、苹果处理、手机安装）大约 15 到 40 分钟。一天最多试几轮到十来轮。
- 没有断点，没有实时日志，没有性能分析工具。音频回调里的问题（爆音、丢缓冲、时间戳错位）往往要看日志和波形才能定位。
- 负责人不审代码，AI 在 Windows 上也看不到真机的任何输出。

所以这个循环只能用来验证“已经在别处证明正确的东西”，不能用来探索算法。实验 S6 会实测循环时间。

【事实】GitHub 托管的 macOS runner 在私有仓库里按 10 倍消耗免费分钟数；公开仓库普遍报道为标准 runner 免费（以 GitHub 官方计费页面为准）。本仓库目前是公开的。

### 4.2 重点路线：算法先做成跨平台库，在 Windows 上离线开发

**【判断】这是没有 Mac 时唯一现实的路线，推荐采用。即使以后有了 Mac，这条路线也是对的。**

做法：

1. **核心库**只做一件事：输入“音频采样加谱面”，输出“判定事件”。不碰任何 iOS 接口，不读文件，不分配内存（实时线程规矩）。
2. **评测台**在 Windows 上运行：读录音文件和标注，调用核心库，输出指标表。每次改算法都跑一遍。
3. **iOS 壳**尽量薄：采集音频、调核心库、画界面、播伴奏。
4. **真机录音回放一致性**：iOS 壳必须能把收到的原始输入存成文件并导出。同一份文件在 Windows 评测台上重放，判定结果必须和真机上完全一样。这样真机上发现的任何误判都能带回 Windows 复现和修复。

语言选择：

| 选项 | 评价 |
|---|---|
| C++ 核心库 + 命令行评测程序 + Python 脚本做统计和画图 | **推荐。** Windows 和 iOS 都原生支持；Swift 调用 C++ 是成熟路径；Cycfi Q 就是 C++，方便对照；实时安全 |
| Rust 核心库 | 安全性更好，Windows 上工具链体验好。但接到 iOS 多一层构建配置，音频领域可抄的例子少。可行，不首选 |
| 纯 Python 原型，再移植 | 探索最快。但“原型一份、正式一份”正是工程规矩要禁止的并存。只允许做限期的一次性实验 |
| 纯 Swift | 在 Windows 上没法正常开发和评测。排除 |

具体安排写在 ADR-005（已确定，语言选 C++ 的理由也在那里）：算法探索可以用 Python 做有期限的实验；一旦选定，正式实现只有 C++ 一份；Python 只保留评测、统计、标注工具的角色。

### 4.3 其他选项的代价

| 选项 | 能得到什么 | 代价和限制 | 建议 |
|---|---|---|---|
| 维持现状，只用 CI | 零新增成本 | 见 4.1 | 阶段 0 和阶段 1 完全够用 |
| 云端 Mac（按小时或按月租） | 能用 Xcode 和模拟器 | 【事实】云端机器接不了你手边的 iPhone 和音频接口，无法做真机调试和回环测试。【推测】费用大约每月几十美元起，需核实。对实时音频帮助很小 | 不建议 |
| 二手 Mac mini（苹果芯片） | 真机连线调试、实时日志、性能分析；几十秒装一次机；还能当自托管的 CI runner；AI 编程工具可以在上面自己完成“构建、运行、看日志”的循环 | 【推测】一次性几百美元量级，需核实行情；占一点桌面 | **建议在阶段 2 开始时买** |

【判断】阶段 0 和阶段 1 不需要 Mac，现在不用买。到了阶段 2，一台二手 Mac mini 的价格相对于它省下的时间很划算，尤其因为负责人靠 AI 写代码：有了 Mac，AI 才能自己看到真机上发生了什么。负责人已决定：现在不买，以后会买（他的其他项目也需要）。具体时间在实验 S6 之后定。

## Q5. 边学边造的学习闭环

细节在 `05_LEARNING_LOOP.md` 和 `04_CURRICULUM_DRAFT.md`，这里只写结论。

### 5.1 踩坑日志

- 每次练习后填一份，目标 3 分钟，大部分是勾选。模板在 `templates/PRACTICE_LOG.md`。
- 每周做一次 15 分钟回顾，可以让 AI 先汇总。同一个卡点出现三次以上，才允许升级：升级成一张“方法论卡片”、一条 App 需求、或一个要问老师的问题。
- 方法论卡片用“现象、假设、干预、证据、状态”五栏，把学琴当成只有一个被试的实验来记。这正好用得上负责人的心理学训练。
- App 需求必须能追溯到至少三条日志。没有日志支撑的功能不做。

### 5.2 练习录音再利用

- 录音是接口干声，48 kHz、24 bit、单声道 WAV，不加任何处理。
- 录音属于个人数据，放在仓库之外，仓库里只放清单和标注（见 ADR-008）。
- 标注分三层：练习谱面自带的“意图标签”；离线高精度算法自动出的“建议标签”；人工确认过的“金标准”小集合。人只需要看前两层不一致的地方。
- 自然弹错的片段最宝贵，另外再专门录一批故意弹错的。
- 评测集按录音场次划分成开发集和留出集，同一场录音不能两边都出现。

### 5.3 课程从哪里来

**【判断】不自己设计课程。选一套成熟的零基础课程作主干，App 的练习只是把主干里每一课的练习点改写成原创短练习。**

粗略骨架分七个阶段，演奏处理（闷音、音长、律动、跟鼓）从第一阶段就开始，音色处理分四层逐步引入。两条分支（J-pop 和爵士）在共同基础之后才分开。详见 `04_CURRICULUM_DRAFT.md`。

真人老师在三个节点介入：开始的头两周（姿势和手型）、第二阶段结束（录像评审）、以及对整份课程骨架做一次评审。

### 5.4 App 能评判什么，不能评判什么

| 能自动评判（接线干声） | 把握程度 |
|---|---|
| 音高对不对 | 高 |
| 起音早了还是晚了、速度稳不稳 | 高 |
| 该休止的地方有没有声音 | 较高 |
| 音长够不够、有没有提前断 | 【推测】中等，需实验 |
| 力度是否均匀 | 中等 |
| 上一个音有没有止住 | 【推测】待验证，见 2.5 |

| 不能评判 | 替代方式 |
|---|---|
| 姿势、持琴、手腕角度 | 示范视频；每月一次手机录像和示范并排看；老师 |
| 左手手型、用了哪根手指 | 自检清单；录像回看 |
| 同一个音是在哪根弦哪一品弹的 | 单路音频分不出来。谱面标注加自检。远期见 Q8 |
| 发力、紧张、疼痛 | 日志里有“身体不适”一栏；一出现疼痛就停，问老师 |
| 音色好不好听 | 不评分。提供对比练习，让用户自己听 |
| 律动“有没有味道” | 只给时间统计数据。请老师或和原曲对比着听 |

## Q6. 造工具与练琴之间的平衡

### 6.1 防范机制

**【判断】头号风险确实是“造工具成了逃避练琴的正当理由”。** 下面的机制写进了路线图的关卡和工程规矩，不靠自觉。

1. **两本账。** 每周记录练琴分钟数和开发分钟数（包括和 AI 讨论方案、审阅、真机测试）。日志模板里有这两栏。
2. **先练后造。** 当天没练琴，当天不碰开发。本周开发时间不超过上周练琴时间。
3. **最低练琴额度。** 提议每周 5 次、每次 20 分钟。连续两周没达到，开发冻结，只允许写日志。
4. **无日志不开工。** 每个开发任务必须引用至少三条日志里的同一个痛点。
5. **关卡绑定学习进度。** 路线图每道关卡都有练琴方面的条件。琴没练到，App 就不能进入下一阶段。
6. **允许的结局包括“不造了”。** 每个阶段结束时问一次：造工具有没有帮到学琴？如果现成工具够用，停止开发、继续学琴并沉淀方法论，同样算项目成功。

因为代码由 AI 写，负责人的“开发时间”其实是决策和验收时间，本来就不多。真正要防的是花大量时间和 AI 讨论架构、看方案，而琴放在一边。

### 6.2 先买还是先造

**【判断】先买。**

- 阶段 0 不写应用代码。用一套成熟课程学琴，同时用一到两个现成的互动 App 接上接口练习，把踩坑日志、竞品实测、自己的录音三样东西攒起来。
- 理由：零基础阶段最缺的是正确的入门引导，这是现成课程已经做得很好的事；现在还不知道自己真正的痛点是什么；竞品接上接口之后到底行不行，只有实测才知道。

**自己的 App 从什么时候开始出现：** 同时满足三个条件之后。

1. 已经有至少 20 次有日志的练习，跨度至少 4 周。
2. 竞品实测做完，并且日志里有一个反复出现、现成工具解决不了的具体痛点。
3. 阶段 1 的离线算法在自己的录音上过了关卡 G1。

在此之前，手机上最多只出现一个“探针”：只会录音、显示电平、导出文件的诊断小程序，用来做实验 S5 和 S6。它不是产品。

**第一个版本只解决哪一个问题：** 由日志决定，不由评审决定。评审员的预测是：

> 【推测】最可能的第一痛点是“慢速单音练习时，我不确定 App 的判定可不可信”。对应的第一版是一个只做一种练习的可信判定器：慢速根音或空弦练习，告诉我音对不对、早了还是晚了、或者没听清，并且在接入有问题时先告诉我是接入的问题。

如果日志显示第一痛点其实是“不知道今天该练什么”或者“坚持不下来”，那第一版就应该是练习计划和记录工具，检测算法往后排。要接受这种可能。

### 6.3 竞品实测方案

完整方案在 `06_BENCHMARK_PROTOCOL.md`。要点：

- 同一把琴、同一套弦、同一个接口、同一个增益位置、同一天、测试顺序随机。
- 同一组测试乐句，覆盖最低音、同音连弹、跨弦余音、轻重力度、故意弹错、完全不弹。
- 竞品不能导入任意乐句，所以分三类测试：调音器类（看识别速度和稳定性）、课内测试（选各家最接近的课程）、自研算法专用（完整乐句清单）。
- 全程手机录屏留证据，每个音符记一行。
- 指标不只是“准确率”，而是分开报告：弹对判错、弹错判对、不弹却得分、没听清、主观延迟、接入折腾程度。
- 同一份方案和同一批录音，以后就是自研算法的评测基准。

## Q7. 内容和版权

这不是法律意见，只是划出需要注意的边界。

**【判断】现阶段的边界：自己学、自己用、不给别人。**

- 自己写的练习、自己录的伴奏、自己合法购买的教材和音源，用于自己练习，风险很低。
- 把买来的歌曲在自己电脑上降速、循环、分离声部来练，只要文件不离开自己的设备，也属于个人使用的范围。
- 不要绕过任何技术保护措施去获取音源。

**边界在“向他人提供”这四个字。下面这些都算向他人提供：**

- **提交到公开的 GitHub 仓库。本仓库现在是公开的。** 教材的扫描页或抄下来的练习、商业歌曲的谱面、伴奏、分离出来的声部，哪怕只是自己用，也不能提交进来。
- 通过 TestFlight 发给别人，或者上架。
- 把带原版伴奏的练习视频发到网上。
- 把课程内容、谱面发给朋友。

**以后如果要分享或发布，这些东西必须重新审查：**

1. 所有练习和谱面：是不是原创，有没有照搬教材或课程。
2. 所有伴奏和音源：作品权利和录音权利是两层，都要有着落。
3. 歌曲名、艺人名的使用方式。
4. 鼓和其他乐器的采样包、音色库的许可范围。
5. 所有开源依赖的许可（尤其是 GPL 和 AGPL）。
6. 示范视频里出现的老师、音乐、教材。
7. 竞品实测结果能否公开（各家服务条款可能限制发布评测）。
8. 请老师参与的内容，权利归属有没有写清楚。
9. 自己的练习录音和日志里的个人信息。

## Q8. 远期构想：MIDI 化和分弦拾音

**不影响主路线。只在架构上留口子。**

### 8.1 能带来什么

| 能力 | 说明 |
|---|---|
| 知道是哪根弦 | 每根弦单独一路信号，直接知道哪根弦在响 |
| 知道是哪一品 | 弦加音高就能算出品位。于是可以做把位和指法路线的反馈 |
| 每根弦都是干净的单音 | 余音重叠的问题消失。还能直接看到“哪根弦没止住”，闷音反馈会准很多 |
| 双音和和弦 | 多根弦同时响也能分开识别 |

### 8.2 不能解决什么

- **低音周期带来的物理延迟还在。** 只要是从弦的振动里算音高，E1 至少要等一到两个周期。分弦只是让信号更干净，能更接近这个下限。
- 仍然不知道是哪根手指按的，不知道姿势和发力。
- 硬件要装在琴上，有成本、安装和校准的负担。

唯一能绕过周期延迟的是**品丝感应**一类的方案（在拨弦之前就知道按的是哪一品），它不靠分析振动。这类产品很小众，需核实现状。

### 8.3 现有方案的大致情况（全部需要核实）

- 分弦拾音器加转换器：Roland 的贝斯用 GK 分弦拾音器配合其合成器或 MIDI 转换设备。
- 分弦拾音器散件：Cycfi 的 Nu 系列多通道拾音器（和 Q 库是同一位作者）。
- 单路音频转 MIDI 的硬件：Sonuus 的贝斯转 MIDI 转换器一类。
- 纯软件音频转 MIDI：Jam Origin 的 MIDI Guitar 及其贝斯版本。
- 品丝感应式 MIDI 贝斯：Industrial Radio 一类的定制乐器。
- 面向吉他的无线 MIDI 拾音系统通常没有贝斯版本。

### 8.4 架构上的口子

判定模块只接收统一的“音符事件”：起音时间、音高（可空）、弦（可空）、品（可空）、力度、置信度、来源。

- 音频路线：音频源 → 检测器 → 音符事件。
- MIDI 路线：MIDI 源 → 音符事件（直接带系统时间戳，弦和品可以从通道推出）。

判定、评分、界面都不需要知道事件是从哪条路线来的。见提议中的 ADR-007。
