# ADR-005 核心算法做成跨平台 C++ 库，在 Windows 上离线先行

- **状态：** 已确定
- **日期：** 2026-11-10
- **提出人：** 评审员（Claude）
- **确认人：** 产品负责人（2026-11-10）

## 背景

开发机是 Windows，没有 Mac。iOS 只能通过“CI 构建 → TestFlight → 真机”来验证，一轮大约 15 到 40 分钟，没有调试器和实时日志。负责人不审代码。

## 决定

1. 检测和判定逻辑做成一个独立的核心库，用 C++ 编写。它只接收音频采样和谱面，输出判定事件；不依赖任何 iOS 接口；在实时路径上不分配内存、不加锁、不做读写。
2. 在 Windows 上提供一个命令行评测程序：读录音和标注，调用核心库，输出事件和指标。统计和画图用 Python 脚本。
3. iOS 端是薄壳：采集、调用核心库、界面、伴奏播放。
4. iOS 端必须能导出原始输入录音和判定事件。同一份录音在 Windows 上重放，结果必须和真机一致（实验 S10）。
5. 算法探索可以用 Python 做有期限的一次性实验，放在 `experiments/`，带过期日期。一旦选定算法，正式实现只有 C++ 一份。
6. 任何检测相关的改动，先通过离线评测，再上真机。

## 理由

- 把最难、迭代最多的部分放在迭代最快的环境里。
- “输入录音、输出事件”的测试，是在没有人审代码的情况下保证质量的主要手段。
- C++ 在 Windows 和 iOS 上都是原生支持的；对照候选 Cycfi Q 也是 C++。

## 为什么是 C++ 而不是 Rust

负责人把语言的选择交给评审员定。结论是 C++，理由按重要程度排：

1. **接到 iOS 最省事。** Xcode 直接编译 C++，Swift 调用 C++ 是苹果官方支持的路径，不需要额外的工具链。Rust 要多装一套编译目标、多一层桥接生成工具，CI 上的配置更长。没有 Mac、只能靠 CI 排错的情况下，构建链越短越好。
2. **可以参考和对照的音频代码几乎都是 C++。** 对照候选 Cycfi Q 就是 C++ 库，可以直接放进同一个评测程序里比较。
3. **施工方两种都能写。** Codex 写 C++ 和 Rust 都没有问题，这一条不构成区别。
4. **Rust 的主要好处在这里用不上多少。** Rust 强在防止内存错误和多线程错误。核心库是一个单线程、不分配内存的小型计算模块，这类错误的空间本来就小，并且有“同一份录音、结果必须一致”的测试兜底。

代价：C++ 不会自动阻止内存错误。对策是 CI 里打开内存和未定义行为检查工具来跑全部测试。

如果以后施工中发现 C++ 的构建或质量问题持续拖慢进度，可以提议改用 Rust；改的时候本条其余各项不变。

## 备选

- Rust：见上。可行，不首选。
- 纯 Swift：在 Windows 上无法正常开发和评测。排除。
- Python 原型加移植：会造成两份实现并存。只允许作为限期实验。

## 后果

- 仓库里会有 C++、Swift、Python 三种语言，CI 从第一次提交起要覆盖全部。
- Swift 调用 C++ 需要一层桥接。
