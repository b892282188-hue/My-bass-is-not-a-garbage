# 05 学习闭环：日志、录音、从日志到方法论再到需求

这个项目最独特的资产，是一个零基础初学者从头开始的真实踩坑记录。这份文件规定怎样把它留下来、用起来。

```text
练琴 ──► 踩坑日志（每次 3 分钟）──► 周回顾（每周 15 分钟）
  │                                      │
  └► 练习录音 ──► 标注 ──► 测试集        ├──► 方法论卡片
                            │            ├──► App 需求（引用日志）
                            ▼            └──► 问老师的问题
                      算法评测 ◄── App 改动必须先过评测
```

## 1. 踩坑日志

### 1.1 原则

- **每次练习后立刻填，3 分钟以内。** 超过 3 分钟说明模板太长，删栏位。
- **大部分是勾选，只有两三处写一句话。**
- **记卡点，不记流水账。** 今天顺利就只填前四栏。
- **宁可粗糙也不要断。** 断了三天以上，周回顾时第一件事是找出为什么断。

### 1.2 填在哪里

模板是 `templates/PRACTICE_LOG.md`。日志含个人信息，本仓库是公开的，所以**日志不放在本仓库**。负责人已决定：另建一个私有仓库存放日志。建议每次练习开一个 issue，用模板填。这样手机上用 GitHub App 就能填，AI 也能直接读取和汇总。

### 1.3 栏位为什么这样设

| 栏位 | 用途 |
|---|---|
| 日期、练琴分钟、开发分钟 | 两本账（`01_FEASIBILITY.md` Q6） |
| 练了什么、用了什么工具 | 把卡点和课程阶段、工具对上 |
| 卡在哪里（一句话） | 核心 |
| 卡点类型（勾选） | 让周回顾能计数 |
| 我猜原因 | 这是假设。日后回看它对不对，本身就是方法论的材料 |
| 当时希望有什么帮助 | 需求的原始形态 |
| 工具判定可信吗 | 竞品和自研 App 的长期实测数据 |
| 身体有没有不适 | 安全阀 |
| 自我感觉 1 到 5 | 动力曲线，预警放弃的风险 |
| 录音文件名 | 把日志和录音连起来 |

## 2. 周回顾

每周一次，15 分钟。可以先让 AI 读完本周日志，按下面的格式出一份草稿，负责人改。

1. **两本账：** 本周练琴几次、多少分钟；开发多少分钟；有没有达到额度。
2. **卡点计数：** 按类型统计；列出本周重复出现的卡点。
3. **升级判断：** 对每个累计出现三次以上、跨了至少两周的卡点，选一个去向：
   - 写成或更新一张方法论卡片；
   - 变成 App 需求；
   - 变成问老师的问题；
   - 继续观察。
4. **上周的干预有没有效果：** 回看方法论卡片里“验证中”的条目。
5. **下周只改一件事。**

**升级成 App 需求的条件（全部满足）：**

- 同一个卡点至少三条日志，跨至少两周。
- 现成工具、主干课程、老师的建议都试过，解决不了或者太费事。
- 能写出“做完之后，日志里应该看到什么变化”。

## 3. 从日志到方法论

### 3.1 方法论卡片

每张卡片一个文件，五栏：

| 栏 | 内容 |
|---|---|
| 现象 | 反复出现的是什么。引用日志日期 |
| 假设 | 我认为原因是什么 |
| 干预 | 我打算怎么改练习方式，改多久 |
| 证据 | 改之前和之后的对比：日志里的频次、App 的统计、录音 |
| 状态 | 猜想、验证中、已验证、已推翻 |

### 3.2 为什么这样设计

【判断】这其实是把学琴当成只有一个被试的实验来做：先写下预测，只改一个变量，前后对比。负责人的心理学背景在这里正好用得上。几条建议：

- **干预之前先写下预测。** 事后才想的解释不算数。
- **一次只改一件事。** 不然不知道是什么起了作用。
- **被推翻的卡片不删。** “我以为是 A，其实是 B”是方法论里最有价值的部分。
- **区分“对我有效”和“普遍有效”。** 单人记录只能支持前者。以后如果要对外讲，要说清这一点。

### 3.3 沉淀成文

每过一个课程阶段，把状态为“已验证”和“已推翻”的卡片汇总成一篇阶段小结：这个阶段我以为会难在哪里、实际难在哪里、什么办法有效。这些小结就是方法论的初稿。

## 4. 练习录音再利用

负责人自己的接线干声，是算法最真实的测试集。

### 4.1 录什么

| 类别 | 内容 | 什么时候录 |
|---|---|---|
| 基准乐句 | `06_BENCHMARK_PROTOCOL.md` 的乐句清单，每条多遍 | 阶段 0 录一套；以后每过一个课程阶段重录一套，记录技术的变化 |
| 日常练习 | 每次练习最后 5 分钟，跟节拍器弹当天的内容 | 尽量每次 |
| 故意弹错 | 错半音、错弦、错八度、漏音、多音 | 和基准乐句一起录 |
| 自然出错 | 日常练习里真实的错误 | 不用专门录，标注时挑出来。这是最宝贵的 |
| 不弹 | 只放伴奏或节拍器，手按住弦 | 和基准乐句一起录 |

### 4.2 怎么录

- **格式：** 48 kHz、24 bit、WAV，不加任何效果和处理。
- **在哪录：** 接口接 Windows 电脑，用免费的录音软件。（阶段 2 以后，App 自己会导出原始输入。）
- **时间基准：** 如果接口有两路输入，把节拍器的声音用一根线回录到第二路。这样琴声和节拍在同一个文件里，采样级对齐，不需要事后猜延迟。只有一路输入时，录音开头先拨一下弦同时让节拍器响一拍，作为对齐标记，并在元数据里注明精度较低。
- **每次录音前记下：** 接口增益位置、琴上旋钮位置、弦的新旧。

### 4.3 存在哪里

**录音是个人数据，不进任何公开仓库。**（工程规矩第 8 条，ADR-008。）

```text
BassData/                      ← 仓库之外，本机硬盘，备份到 Google Drive
  recordings/
    2026-11-15_s01/            ← 一次录音场次一个目录
      T03_open-E_bpm60_take1.wav
      T03_open-E_bpm60_take1.json   ← 元数据
  labels/
    2026-11-15_s01/
      T03_open-E_bpm60_take1.labels.csv
  manifest.csv                 ← 全部文件的清单：路径、校验值、场次、乐句、标注层级、划分
```

- 文件名规则：`乐句编号_简述_bpm速度_take序号.wav`。
- 元数据记录：日期、场次、乐句编号、速度、琴、弦、接口、增益位置、旋钮位置、录音软件、有没有节拍基准通道、备注。
- 清单和标注文件体积小，可以放进私有仓库做版本管理。音频本身不进 git。
- 备份位置：负责人的另一个 Google 账号的 Drive。
- **清理规则。** 负责人打算定时清理 Drive。录音是算法的测试集，清理时按下面的规则来，避免把测试集删掉：

| 录音 | 能不能清理 |
|---|---|
| 基准乐句录音（每个课程阶段一套） | 永久保留 |
| 已经有金标准标注的录音 | 永久保留 |
| 在 `manifest.csv` 里被标为开发集或留出集的录音 | 永久保留 |
| 真机上导出的、对应某个已修误判的输入录音 | 永久保留 |
| 没进清单的日常练习录音 | 保留 30 天后可以删。删之前过一眼有没有值得留下的自然出错片段 |

  `manifest.csv` 是判断依据：清单里有的不删，清单里没有的才可以清。

**CI 用的小测试集：** 工程规矩要求测试集必须包含真实录音。建议从基准乐句里挑一小批（总共不超过 20 MB、只有单音的短片段），经负责人逐个同意后放进仓库的 `tests/fixtures/real/`。完整测试集留在本机，评测结果以报告的形式提交。负责人已同意，每个文件放进去之前仍由他点头。

### 4.4 怎么标注

三层，成本由低到高：

| 层 | 是什么 | 怎么来 | 用途 |
|---|---|---|---|
| 意图标签 | 这段录音打算弹什么：乐句的谱面 | 录的时候就有，零成本 | 所有录音都有 |
| 建议标签 | 每个音实际的起音时刻和音高 | 离线跑不受延迟限制的高精度算法（长窗口的 pYIN 或神经网络），自动生成 | 所有录音都有 |
| 金标准 | 人确认过的起音时刻、音高、对错、特殊情况（余音、闷音、杂音） | 人只看“意图标签和建议标签不一致”的地方，在波形软件里确认或修正 | 一个小集合，覆盖乐句清单的每个类别 |

标注文件每行一个音符：起音时刻、结束时刻、实际音高、预期音高、类别（正确、错音、漏、多、闷音、不确定）、备注。

**“不确定”是合法的标注。** 人也听不清的音，不应该强行要求算法判对或判错，评测时单独统计。

标注成本用实验 S11 量一次。

### 4.5 怎么划分和评测

- **按场次划分。** 同一次录音场次的文件，要么全在开发集，要么全在留出集。留出集不参与调参。
- **留出集比例**大约三成，并且每个乐句类别都要有。
- **新录音优先进留出集**，旧的留出集可以轮换进开发集。
- **评测命令只有一个。** 输入清单和算法版本，输出一张指标表，按乐句类别和音高分组。指标定义见 `06_BENCHMARK_PROTOCOL.md`。
- **真机上发现的误判**：导出当时的原始输入，标注后加入测试集。每个修掉的误判都留下一个永久的测试用例。

## 5. 从日志到 App 需求

每条需求是一个任务，必须包含：

1. **痛点：** 一句话。
2. **证据：** 至少三条日志的链接或日期。
3. **现成办法为什么不够。**
4. **做完之后日志里应该看到什么变化。**
5. **验收：** 涉及检测的，写明要通过哪些离线测试用例。
6. **不做什么。**

上线两周后回看日志，把结果写回任务：痛点缓解了、没变化、或者引出了新问题。没变化的改动要回滚或重做。
